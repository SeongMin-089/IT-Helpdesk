# IT-Helpdesk 요구사항 명세서

> 기준 문서: `docs/requirements.md`  
> 대응 데이터 모델: `docs/erd.drawio` (2026-10-20 검토본)  
> 프로젝트: Odoo 19 Community 기반 사내 IT 장애 접수 및 해결 관리 시스템  
> 범위 구분: **1차 필수 구현 / 2차 고도화 / 추후 결정**

## 1. 프로젝트 개요

### 1.1 프로젝트명
IT-Helpdesk — Odoo 기반 사내 IT 장애 접수 및 해결 관리 시스템

### 1.2 프로젝트 목적
사내 직원의 IT 장애 접수부터 담당자 배정, 처리, 해결, 종료까지의 흐름을 통합 관리한다. 상태·담당자·긴급도·조치 내역의 변경 이력을 보존하고, 긴급 문의를 우선 처리할 수 있게 한다. 향후 역할별 대시보드와 해결 사례 재활용 기능으로 확장한다.

### 1.3 개발 환경
- 플랫폼: Odoo 19 Community
- 언어: Python 3.12, XML
- DB: PostgreSQL 17
- 개발 도구: VS Code
- 형상 관리: Git / GitHub
- 기간/형태: 10영업일 / 개인 프로젝트

### 1.4 개발 범위
- **1차:** 네트워크·인터넷, PC·노트북, 소프트웨어, 프린터·주변기기, 계정·접근 관련 **IT 장애** 접수 및 처리
- **2차:** 대시보드, 유형별 자동 배정, FAQ·해결 사례
- **범위 밖:** 소프트웨어 설치 요청, 계정 발급, 장비 지급, 접근 권한 신청 등 **IT 서비스 요청**과 AI 자동 분류, IT 자산 관리, 복잡한 SLA 및 실제 이메일 알림 연동

## 2. 사용자 역할과 접근 권한

### 2.1 일반 직원(Requester)
- 본인 문의 등록·조회, 댓글·첨부파일 작성 및 처리 이력 조회
- **접수 상태이면서 미배정인 본인 문의** 수정 및 아카이브
- **해결 상태인 본인 문의**의 종료 승인 또는 사유를 작성한 재처리 요청
- 2차: 본인 대시보드, 공개 FAQ 조회

### 2.2 담당자(Agent/관리자)
- 모든 문의 조회·관리. 종료 전 문의는 업무 규칙에 따라 수정 가능하며, 종료된 문의의 내용·상태·댓글·첨부는 수정 불가. 문의 보관·복원은 별도 관리 기능으로 수행
- 처리 담당자 수동 배정·변경, 상태 전이, 해결 내용 작성
- 긴급도 조정, 댓글·첨부파일 관리 및 이력 열람
- 유형 관리(1차), 전체 대시보드·FAQ 관리·자동 배정(2차)

### 2.3 역할별 권한표

| 기능 | 일반 직원 | 담당자(관리자) |
|---|---|---|
| 로그인 및 문의 등록 | 가능 | 가능 |
| 조회 | 본인 문의만 | 전체 문의 |
| 문의 수정 | 본인 + 접수 + 미배정 | 종료 전 문의만 허용된 업무 규칙 내에서 수정; 종료 후 일반 수정 불가 |
| 문의 삭제 | 본인 + 접수 + 미배정일 때 아카이브 | 관리 기능으로 아카이브·복원 가능(종료 문의 포함); 실제 삭제 없음 |
| 처리 담당자 배정 | 불가 | 가능 |
| 상태 변경 | 해결→종료 / 해결→처리 중(재처리) | 접수→배정→처리 중→해결 |
| 댓글·첨부파일 | 본인 문의, 종료 상태 제외 | 전체 문의, 종료 상태 제외 |
| 변경 이력 조회 | 본인 문의 | 전체 문의 |
| 유형 관리 | 불가 | 가능 |
| 공개 FAQ 조회(2차) | 가능 | 가능 |
| FAQ 작성·공개(2차) | 불가 | 가능 |

권한은 Odoo **그룹(`res.groups`)**, **모델 ACL(`ir.model.access`)**, **레코드 규칙(`ir.rule`)**으로 제한한다. 상태 변경·특정 필드 수정·아카이브·첨부파일 접근처럼 ACL만으로 보장하기 어려운 조건은 **서버 메서드에서도 검증**한다. 단순히 메뉴나 버튼을 숨기는 것으로 권한을 구현하지 않는다.

## 3. 기능 요구사항

### 3.1 1차 필수 기능

|---|---|---|
| FR-01 | 로그인 | Odoo 기본 사용자 인증 사용 |
| FR-02 | 권한 | 직원 / 담당자 그룹과 서버 측 데이터 접근 제어 |
| FR-03 | 문의 등록 | 제목·내용·유형·긴급도·위치 필수, 연락처·첨부 선택 |
| FR-04 | 문의 조회 | 직원은 본인 문의, 담당자는 전체 문의 |
| FR-05 | 문의 수정 | 직원은 접수·미배정인 본인 문의만, 담당자는 관리 권한에 따라 수정 |
| FR-06 | 문의 삭제 | **실제 행 삭제 대신 `active=False` 아카이브**; 직원은 접수·미배정 본인 문의만 |
| FR-07 | 검색·필터 | 제목·유형·상태·긴급도·담당자 기준 검색 및 필터 |
| FR-08 | 페이징 | Odoo 기본 목록 페이징 이용 |
| FR-09 | 수동 배정 | 담당자가 처리 담당자 지정·변경, 이력 남김 |
| FR-10 | 상태 관리 | 접수→배정→처리 중→해결→종료 및 허용된 재처리 전이 |
| FR-11 | 변경 이력 | 상태·담당자·긴급도·재처리·해결 조치의 변경 기록 |
| FR-12 | 댓글 | 본인 문의 또는 관리 권한이 있는 문의에 댓글 작성·조회 |
| FR-13 | 첨부파일 | 이미지·문서 첨부 및 권한 검증 |
| FR-14 | 종료 확인 | 요청자가 해결 상태 문의를 종료 |
| FR-15 | 재처리 요청 | 요청자가 해결 상태에서 **사유를 필수 입력**하여 처리 중으로 되돌림 |
| FR-16 | 긴급도 | 낮음/보통/높음/긴급 4단계 |
| FR-17 | 긴급 우선 표시 | 긴급도별 정렬과 시각적 강조, `priority_order` 저장형 계산 필드 활용 |
| FR-22 | 문의 번호 | `ir.sequence`로 `HD-00001` 형식의 고유 문의 번호 자동 발급 |

| FR-24 | 해결 방식 | 담당자가 해결 처리 시 현장 방문/원격·안내 중 하나를 선택해 기록 |

### 3.2 2차 고도화 기능

| ID | 기능 | 요구사항 |
|---|---|---|
| FR-18 | 역할별 대시보드 | 직원 개인·담당자 전체 접수/진행/해결 현황 |
| FR-19 | 자동 담당자 배정 | 유형별 `default_user_id`가 있으면 지정된 담당자 자동 배정; 미설정이면 미배정 유지 |
| FR-20 | FAQ 관리 | 담당자가 FAQ 작성·수정·보관·공개 여부 관리; 직원은 **공개된 FAQ만** 조회 |
| FR-21 | 해결 사례 활용 | 해결된 문의를 참고해 FAQ 초안 작성; **검토 후 담당자가 수동 공개** |

2차 기능은 1차 기능 구현 및 테스트가 끝난 후 진행한다. **FR 번호는 기존 명세서와의 추적성을 유지**하기 위해 추가 기능에 FR-22~24를 부여했다.

## 4. 입력 항목과 검증

| 항목 | 필수 | 검증 |
|---|---|---|
| 문의 제목 `name` | 필수 | 공백 제외 5~100자 |
| 내용 `description` | 필수 | 공백 제외 10~5,000자 |
| 유형 `category_id` | 필수 | 유효한 유형 선택 |
| 긴급도 `priority` | 필수 | 낮음·보통·높음·긴급 |
| 발생 위치/부서 `location` | 필수 | 공백 제외 2~100자 |
| 연락처 `contact` | 선택 | 입력 시 전화번호 형식 검사 |
| 첨부파일 | 선택 | 허용 확장자/최대 용량은 구현 전 결정 |

- 제목과 내용에는 공백만 입력할 수 없다.
- 요청자 `requester_id`는 로그인한 계정으로 자동 지정한다. 일반 직원이 임의 요청자를 지정할 수 없다.
- 초기 상태는 `received`(접수), 최초 배정자 `assigned_user_id`는 비어 있다. **2차 자동 배정 활성화 시 초기 배정/상태 규칙은 별도 확정한다.**
- 발급 번호는 `ir.sequence`의 `HD-00001` 형식을 사용하며 중복을 허용하지 않는다.
- `create_date`, `write_date` 등 기본 생성·수정 기록은 Odoo에서 관리한다.
- 필수값, 길이, 권한, 상태 전이는 서버 측에서 검증하고 오류 메시지를 표시한다.

### 4.1 문의 유형 초기 데이터

| 코드 | 명칭 | 예시 |
|---|---|---|
| `NETWORK` | 네트워크 / 인터넷 | Wi-Fi 연결 실패, 인터넷 불가 |
| `HARDWARE` | PC / 노트북 | 부팅 오류, 블루스크린 |
| `SOFTWARE` | 소프트웨어 | 앱 실행 오류 |
| `PERIPHERAL` | 프린터 / 주변기기 | 인쇄 오류, 장치 인식 실패 |
| `ACCOUNT` | 계정 / 접근 | 로그인 실패, 계정 잠금 |
| `ETC` | 기타 | 위 유형 외 장애 |

유형의 코드 `code`는 유일하다. 사용 여부는 `active`로 관리한다.

## 5. 상태와 업무 흐름

| 내부 값 | 표시명 | 의미 |
|---|---|---|
| `received` | 접수 | 문의 등록, 담당자 미배정 |
| `assigned` | 배정 | 처리 담당자 지정 |
| `in_progress` | 처리 중 | 담당자가 해결 작업 수행 |
| `resolved` | 해결 | 담당자가 조치 결과 작성 |
| `closed` | 종료 | 요청자가 해결 확인 완료 |

| 이전 상태 | 다음 상태 | 주체 | 조건 |
|---|---|---|---|
| 접수 | 배정 | 담당자 | 처리 담당자 지정 |
| 배정 | 처리 중 | 담당자 | 처리 시작 |
| 처리 중 | 해결 | 담당자 | **해결 내용 `resolution` 및 방식 `resolution_method` 필수** |
| 해결 | 종료 | 해당 요청자 | 해결 확인 |
| 해결 | 처리 중 | 해당 요청자 | **재처리 사유 필수**, 재처리 횟수 증가 |

- 다른 상태 전이는 서버에서 거부한다.
- 상태 변경 시 이전·새 상태·변경자·시간을 History에 남긴다.
- `resolved_date`는 마지막 해결 전환 시각, `closed_date`는 종료 전환 시각을 저장한다.
- 해결 처리 시 `resolution_method`(`onsite`/`remote`)를 선택하며, 처리 방식은 상태(`resolved`)와 별개이다.
- 해결 후 재처리되면 **기존 `resolution`, `resolution_method`와 해결 시각을 History에 보존**한 후 Ticket의 현재 `resolution`, `resolution_method`, `resolved_date`를 초기화한다. 과거 해결 정보는 삭제하지 않는다.
- 재처리 시 기존 담당자는 유지하고 `reopen_count`를 1 증가시키며, 재처리 사유와 변경 주체·시각을 History에 기록한다. 재해결 시 새 해결 방식·결과·시각을 다시 저장한다.
- 종료(`closed`) 후에는 일반 직원과 담당자 모두 본문·상태·긴급도·담당자·댓글·첨부파일의 일반 수정이 불가능하다. **담당자(관리자)의 별도 아카이브·복원 관리 작업만 허용**한다.

## 6. 긴급도 관리

| 내부 값 | 표시명 | 시각적 강조 |
|---|---|---|
| `low` | 낮음 | 회색 |
| `normal` | 보통 | 파란색 |
| `high` | 높음 | 주황색 |
| `urgent` | 긴급 | 빨간색 |

- 요청자가 등록할 때 지정하고, 담당자는 이후 변경할 수 있다.
- 변경 전후 긴급도·변경자·변경 시각을 History에 남긴다.
- 저장형 계산 필드 `priority_order`를 `priority` 값에 따라 자동 산출·저장한다: `urgent=4`, `high=3`, `normal=2`, `low=1`. 사용자는 이 내부 값을 직접 수정할 수 없다.
- 담당자 전체 문의 목록 기본 정렬은 **`priority_order DESC, create_date ASC`**로 설정한다. 긴급도가 같으면 더 먼저 등록된 문의를 우선 표시하며, 긴급도 변경 시 계산 필드를 자동 갱신한다.
- 직원 내 문의 목록 기본 정렬은 최신 등록순이고, 선택 정렬에 긴급도순을 제공한다.

## 7. 담당자 배정

### 7.1 1차: 수동 배정
- 담당자 권한이 있는 사용자가 `assigned_user_id`를 지정·변경한다.
- 최초 배정 시 접수→배정 상태 전이와 배정 이력을 함께 기록한다.
- 재배정 시 이전/새 담당자, 변경자, 시각을 History에 남긴다.
- 미배정 문의 목록/필터를 제공한다.

### 7.2 2차: 자동 배정
- 유형(`category_id`)의 기본 담당자(`default_user_id`)가 유효하게 설정된 경우 자동 지정한다.
- 기본 담당자가 없으면 미배정으로 유지한다.
- 자동 배정 이후에도 담당자가 수동 재배정할 수 있으며 이력을 남긴다.
- **자동 배정의 실행 시점 및 최초 상태 처리 규칙은 구현 전에 결정한다.**

## 8. 댓글·첨부파일·변경 이력

### 8.1 댓글 및 첨부파일
- Odoo `mail.thread`/Chatter의 댓글(`mail.message`)과 첨부(`ir.attachment`)를 활용한다.
- 직원은 본인 문의, 담당자는 관리 가능한 문의에만 접근한다.
- 댓글의 작성자·작성 시각을 확인할 수 있게 한다.
- 첨부 조회/다운로드 역시 서버 측 권한을 확인한다.
- 첨부 형식은 JPG, PNG, PDF, DOCX, XLSX, TXT, **최대 5개·파일당 10MB를 설계 목표**로 한다. Odoo 19 기본 첨부 처리와 서버 검증 구현 방식을 확인하기 전에는 적용 완료로 간주하지 않는다. 댓글 수정/삭제 범위는 미확정이다.
- 종료 상태의 문의는 직원·담당자 모두 기본적으로 조회 전용이며 댓글/첨부 추가를 허용하지 않는다(서버에서도 검증).

### 8.2 변경 이력
- `it.helpdesk.history`에 상태 변경, 담당자 변경, 긴급도 변경, 재처리 사유, 해결 조치 변경을 기록한다.
- 항목: 대상 문의, 변경 유형, 이전 값, 새 값, 변경자, 변경 시각, 설명/사유.
- 이력은 **추가 전용(append-only)**으로 취급한다. 일반 사용자의 기존 이력 수정·삭제는 허용하지 않는다.
- 현재 해결 내용은 Ticket `resolution`, 과거 해결 내용/재처리 사유는 History `description` 등으로 보존한다.

## 9. 데이터 모델 및 ERD 기준

**기준 파일: `docs/erd.drawio`**. 테이블은 Odoo 기본 사용자 1개와 프로젝트 전용 모델 4개로 구성한다. 실제 DB 테이블은 Odoo 모델 정의·설치 후 생성된다. 아래는 **논리 설계 기준**이고, Odoo 자체 시스템 필드 및 Chatter 테이블의 모든 컬럼을 나열한 물리 스키마가 아니다.

### 9.1 사용자 — `res.users` / ERD `res_users`
- 참조 필드: `id`(PK), `name`, `login`
- Odoo 기존 모델 재사용; 사용자 테이블을 별도로 생성하지 않는다.

### 9.2 문의 — `it.helpdesk.ticket` / ERD `it_helpdesk_ticket`

| 필드 | 타입/역할 | 비고 |
|---|---|---|
| `id` | ID (PK) | Odoo 기본 식별자 |
| `reference` | Char (고유) | `HD-00001` 형식 |
| `name` | Char | 제목 |
| `description` | Text | 장애 내용 |
| `requester_id` | Many2one → res.users | 요청자, 필수 |
| `assigned_user_id` | Many2one → res.users | 담당자, 선택 |
| `category_id` | Many2one → category | 유형, 필수 |
| `priority` | Selection | 4단계 |
| `priority_order` | Integer (저장형 계산 필드) | `urgent=4`, `high=3`, `normal=2`, `low=1`; 목록 정렬용·사용자 직접 입력 불가 |
| `state` | Selection | 5단계 |
| `contact` | Char | 선택 연락처 |
| `location` | Char | 위치/부서, 필수 |
| `resolution` | Text | 최신 해결 내용 |
| `resolution_method` | Selection | `onsite`(현장 방문), `remote`(원격·안내); 해결 시 필수 |
| `resolved_date` | Datetime | 마지막 해결 시각 |
| `closed_date` | Datetime | 종료 시각 |
| `reopen_count` | Integer | 재처리 누적 횟수 |
| `active` | Boolean | 아카이브 여부 |

### 9.3 유형 — `it.helpdesk.category` / ERD `it_helpdesk_category`
`id`(PK), `name`, `code`(고유), `description`, `default_user_id`(선택; 2차 자동 배정), `active`.

### 9.4 이력 — `it.helpdesk.history` / ERD `it_helpdesk_history`
`id`(PK), `ticket_id`(필수 FK), `change_type`(상태/배정/긴급도/재처리/해결), `old_value`, `new_value`, `changed_by`(사용자 FK), `change_date`, `description`.

### 9.5 FAQ — `it.helpdesk.faq` / ERD `it_helpdesk_faq` (2차)
`id`(PK), `name`, `category_id`(FK), `problem`, `solution`, `source_ticket_id`(선택 FK), `author_id`(사용자 FK), `is_published`(기본 `False`), `active`.

- 담당자가 직접 작성하거나 기존 해결 문의를 기반으로 **FAQ 초안**을 만든다.
- 검토 후 담당자가 수동 공개한다. 직원은 `is_published=True`인 FAQ만 조회한다.
- FAQ 화면에서 참조 원본 문의의 비공개 내용에 접근할 수 없도록 한다.

### 9.6 ERD 관계 (9개)
1. `res_users.id` → `ticket.requester_id`
2. `res_users.id` → `ticket.assigned_user_id` (선택)
3. `category.id` → `ticket.category_id`
4. `res_users.id` → `category.default_user_id` (선택)
5. `ticket.id` → `history.ticket_id`
6. `res_users.id` → `history.changed_by`
7. `category.id` → `faq.category_id`
8. `ticket.id` → `faq.source_ticket_id` (선택)
9. `res_users.id` → `faq.author_id`

댓글과 첨부는 Odoo 기본 모델의 `model`/`res_id` 연결을 재사용하므로 커스텀 테이블을 추가하지 않는다. 사용자 그룹은 Odoo 기본 권한 모델에서 관리한다.

## 10. 화면 구성

**상세 화면 설계 기준 문서: `docs/screen-design.md`.** Odoo 기본 목록(List)·폼(Form)·검색(Search)·Chatter·메뉴를 활용한다. 아래 F-01~F-05의 화면 ID는 개념적 구분으로, 모두 별도 웹페이지 구현을 의미하지 않는다.

| 화면 | 사용자 | 핵심 기능 |
|---|---|---|
| F-01 공통 로그인 | 전체 | Odoo 기본 인증·그룹별 접근 제어 |
| F-02 내 문의 목록 | 일반 직원 | 본인 문의만, 7개 컬럼, 새 문의 등록·검색·필터 |
| F-03 전체 문의 목록 | 담당자 | 전체 문의, 요청자 포함 8개 컬럼, 미배정·내 담당 필터 |
| F-04 문의 등록 | 전체 | 공통 입력폼 및 서버 검증, 요청자 자동 설정 |
| F-05 문의 상세 | 전체 | 공통 정보·Chatter·변경 이력, 상태/권한별 작업 |
| F-05-W01 해결 처리 | 담당자 | 해결 방식·결과 필수 입력 후 상태 전이 |
| F-05-W02 재처리 요청 | 요청자 | 재처리 사유 필수 입력 후 처리 중 전이 |

- **F-02 컬럼:** 번호·제목·유형·긴급도·상태·담당자·등록일. 번호/제목 검색, 상태/유형/긴급도 필터. 기본 최신순. 페이징은 Odoo 기본 기능.
- **F-03 컬럼:** F-02의 7개 + 요청자. 번호/제목/요청자 검색, 상태/유형/긴급도/담당자 필터, 미배정·내 담당 필터. 기본 `priority_order DESC, create_date ASC` 정렬. 미배정 목록은 동일 목록의 사전 필터 메뉴.
- **F-04:** 양 역할 모두 등록 가능. 새 문의 요청자는 로그인 사용자로 자동 설정하고 담당자는 미배정, 상태는 접수로 생성. 유형·제목·내용·긴급도·위치·연락처·첨부 순서. 저장·취소는 Odoo 표준 동작을 우선 사용한다.
- **F-05:** 일반 직원의 수정·아카이브는 접수이면서 미배정인 본인 문의로 제한. 해결 상태에서 종료 확인 또는 사유를 입력한 재처리 요청 가능. 담당자는 배정·처리 시작·해결·우선순위 조정·재배정 수행, 재배정해도 상태 유지. 재처리 시 과거 해결 정보를 History에 보존하고 현재 해결 필드를 초기화한다. 종료 상태는 일반 수정·댓글·첨부가 불가능하며 담당자의 별도 보관·복원 관리 작업만 허용한다.
- **해결 후 미응답:** 1차에서는 해결 상태 유지, 자동 종료 미구현. 향후 정책 검토 시에도 요청자 승인과 시스템 자동 종료를 구분해 기록한다.
- **보안·예외:** 접근 권한, 상태 전이, 필수 해결/재처리 값, 종료 후 변경 금지 등을 UI와 서버 양쪽에서 검증한다.

## 12. 개발 우선순위와 완료 기준

### 12.1 1차 우선순위
1. 모듈 구조, 메뉴, 모델, 보안 그룹/ACL/레코드 규칙
2. 문의 번호·등록·조회·수정·아카이브·입력 검증
3. 검색·필터·페이징과 긴급도 표시
4. 담당자 배정 및 상태 전이와 변경 이력
5. 댓글·첨부파일, 종료 승인·재처리 요청
6. 역할별 접근/예외/업무 시나리오 테스트 및 문서화

### 12.2 2차 우선순위
역할별 대시보드 → 유형별 자동 배정 → FAQ/해결 사례 재활용 (1차 완료 후).

### 12.3 완료 기준
- 직원·담당자 계정으로 로그인, 역할별 접근 제한 확인
- 직원은 본인 문의만, 담당자는 전체 문의 조회
- 문의의 CRUD(삭제는 아카이브), 검색·필터·페이징 구현
- 순번형 문의 번호의 자동 발급·고유성 검증
- 담당자 배정/변경, 허용 상태 전이, 해결 내용 필수 검증
- 상태/배정/긴급도/재처리/해결 변경 이력 조회
- 직원의 해결 승인 또는 사유 있는 재처리 요청
- 댓글·첨부파일 접근 권한 및 기본 동작 검증
- 긴급도별 정렬과 시각적 강조
- 권한 우회 시도, 잘못된 값, 금지된 상태 전이 차단
- README, DB/ERD 자료, 테스트 결과, 주요 화면 캡처와 시연 준비
