## 1. 프로젝트 개요

### 1.1 프로젝트명
IT-Helpdesk — Odoo 기반 사내 IT 장애 접수 및 해결 관리 시스템

### 1.2 프로젝트 목적
사내 직원의 IT 장애 접수부터 담당자 배정, 처리, 해결, 종료까지의 흐름을 통합 관리한다. 상태·담당자·긴급도·조치 내역의 변경 이력을 보존하고, 긴급 문의를 우선 처리할 수 있게 한다. 역할별 대시보드와 유형별 자동 배정, 공개 FAQ 및 해결 사례 재활용을 제공한다.

### 1.3 개발 환경
- 플랫폼: Odoo 19 Community
- 언어: Python 3.12, XML
- DB: PostgreSQL 17
- 개발 도구: VS Code
- 형상 관리: Git / GitHub
- 기간/형태: 10영업일 / 개인 프로젝트

### 1.4 개발 범위
- **1차:** 네트워크·인터넷, PC·노트북, 소프트웨어, 프린터·주변기기, 계정·접근 관련 **IT 장애** 접수 및 처리
- **2차:** 대시보드, 유형별 자동 배정, FAQ·해결 사례
- **범위 밖:** 소프트웨어 설치 요청, 계정 발급, 장비 지급, 접근 권한 신청 등 **IT 서비스 요청**과 AI 자동 분류, IT 자산 관리, 복잡한 SLA 및 실제 이메일 알림 연동

## 2. 사용자 역할과 접근 권한

### 2.1 일반 직원(Requester)
- 본인 문의 등록·조회, 댓글·첨부파일 작성 및 처리 이력 조회
- **접수 상태이면서 미배정인 본인 문의**의 원본 정보(제목·내용·유형·발생 위치/부서·연락처) 수정 및 아카이브. 등록 후 긴급도는 수정할 수 없음
- **해결 상태인 본인 문의**의 종료 승인 또는 사유를 작성한 재처리 요청
- 2차: 본인 대시보드, 공개 FAQ 조회

### 2.2 담당자(Agent/관리자)
- 모든 문의 조회·관리. **저장된 문의의 원본 정보(제목·내용·유형·발생 위치/부서·연락처)는 담당자도 수정할 수 없음**. 일반 `write()`는 **긴급도(`priority`)와 아카이브 여부(`active`)만 허용**하며, 배정·상태 전환·해결 처리는 별도 업무 메서드/Wizard로 수행
- 종료된 문의는 일반 수정·댓글·첨부 추가 불가. 문의 보관·복원은 별도 관리 기능으로 수행(1차 구현 완료)
- 처리 담당자 수동 배정·변경, 상태 전이, 해결 내용 작성
- 긴급도 조정, 댓글·첨부파일 관리 및 이력 열람
- 유형 관리(1차), 전체 대시보드·FAQ 관리·자동 배정(2차)

### 2.3 역할별 권한표

| 기능 | 일반 직원 | 담당자(관리자) |
|---|---|---|
| 로그인 및 문의 등록 | 가능 | 가능 |
| 조회 | 본인 문의만 | 전체 문의 |
| 문의 원본 수정 | 본인 + 접수 + 미배정일 때만 제목·내용·유형·위치·연락처 수정 | **등록 이후 원본 정보 수정 불가** |
| 긴급도 수정 | 최초 등록 시에만 선택 | 종료 전 변경 가능, 전후 값을 History에 기록 |
| 일반 `write()` 허용 필드 | 위 원본 5개 + `active`(보관만) | `priority`, `active`만 허용(종료 시 `active`만) |
| 문의 삭제 | 본인 + 접수 + 미배정일 때 아카이브 | 관리 기능으로 아카이브·복원 가능(종료 문의 포함); 실제 삭제 없음 |
| 처리 담당자 배정 | 불가 | 가능 |
| 상태 변경 | 해결→종료 / 해결→재처리 요청 | 접수→배정→처리 중→해결, 재처리 요청→재처리 중→해결 |
| 댓글·첨부파일 | 본인 문의, 종료 상태 제외 | 전체 문의, 종료 상태 제외 |
| 변경 이력 조회 | 본인 문의 | 전체 문의 |
| 유형 관리 | 불가 | 가능 |
| 공개 FAQ 조회(2차) | 가능 | 가능 |
| FAQ 작성·공개(2차) | 불가 | 가능 |

권한은 Odoo **그룹(`res.groups`)**, **모델 ACL(`ir.model.access`)**, **레코드 규칙(`ir.rule`)**으로 제한한다. 상태 변경·특정 필드 수정·아카이브·첨부파일 접근처럼 ACL만으로 보장하기 어려운 조건은 **서버 메서드에서도 검증**한다. 단순히 메뉴나 버튼을 숨기는 것으로 권한을 구현하지 않는다.

2차 기능은 1차 기능 구현 및 테스트가 끝난 후 진행한다. **FR 번호는 기존 명세서와의 추적성을 유지**하기 위해 추가 기능에 FR-22~24를 부여했다.

### 3.3 FR-18 역할별 대시보드

- 직원 대시보드는 보관되지 않은 본인 문의만 집계한다. 전체, 처리 중(`assigned`, `in_progress`, `reopened_in_progress`), 해결 대기(`resolved`), 종료 완료(`closed`) KPI와 7개 상태 분포 및 최근 5건을 제공한다.
- 담당자 대시보드는 전체 활성 문의를 집계한다. 전체, 미배정(담당자 없음·종료 제외), 진행 중(`assigned`, `in_progress`, `reopen_requested`, `reopened_in_progress`), 긴급 미해결(`urgent`이며 `resolved`, `closed` 제외) KPI를 제공한다.
- 담당자는 7개 상태와 4개 긴급도 분포, 최근 문의 5건, 긴급 미해결 문의 5건을 확인한다.
- 집계 메서드는 로그인 역할을 서버에서 직접 확인한다. 직원 도메인에는 `requester_id = env.uid`, 모든 기본 집계에는 `active = True`를 적용하며 `sudo()`로 Record Rule을 우회하지 않는다.
- KPI·분포·최근 문의는 기존 역할별 목록/상세 액션으로 이동한다. 데이터 없음, 로딩 및 서버 오류 상태를 별도로 표시한다.

### 3.4 FR-20 FAQ 관리 및 FR-21 해결 사례 재활용

- FAQ는 제목 `name`, 해결 방법 `answer`, 선택 유형, 검색 키워드, 공개 여부, 활성 여부, 작성자와 선택 원본 문의를 보관한다. 일반 텍스트 답변을 사용해 임의 HTML·스크립트 삽입 경로를 만들지 않는다.
- IT 담당자는 전체 FAQ를 작성·수정·공개·비공개·보관·복원할 수 있으며 실제 삭제는 허용하지 않는다. 신규 FAQ는 항상 활성 비공개 초안으로 시작하고 공개는 별도 서버 동작으로 수행한다.
- 일반 직원은 ACL과 Record Rule에 따라 `active=True`, `is_published=True`인 FAQ만 조회한다. 원본 문의 필드는 담당자 그룹 필드로 제한해 직접 RPC 읽기도 차단한다.
- 담당자는 `resolved` 또는 `closed` 문의에서 FAQ 초안을 만들 수 있다. 제목·유형·최신 해결 내용만 복사하며 문의 내용, 요청자, 연락처, 위치, 첨부, Chatter와 History는 복사하지 않는다.
- 생성된 초안은 원본 문의와 연결되지만 비공개이며 담당자의 검토와 편집 후 수동 공개한다. 초안 생성은 원본 문의의 상태·해결 정보·History를 변경하지 않는다.

### 3.5 Day 7 추가 기능 — 실시간 공개 FAQ 추천

- 신규 문의 제목에 2자 이상 입력하면 전용 Odoo 19 Char Field Widget이 400ms 디바운스 후 서버 추천을 요청한다. 기존 Form View와 필드 저장 흐름은 유지한다.
- 검색은 공개·활성 FAQ만 대상으로 제목, 키워드, 유형을 토큰 단위로 비교한다. 제목 정확 일치, 제목 부분 일치, 키워드, 유형 순으로 가중치를 부여하고 최대 3건만 반환한다.
- 긴 한국어 조사 결합 표현을 고려해 2~3자 접두 조각도 후보 검색에 사용한다. 동의어는 FAQ의 `keywords`로 관리하며 외부 AI·검색 API는 사용하지 않는다.
- 응답에는 FAQ ID·제목·유형·일반 텍스트 답변 미리보기만 포함한다. 원본 문의 및 요청자·연락처·위치·첨부·댓글·History 정보는 반환하지 않는다.
- 비동기 요청 순번으로 오래된 응답을 폐기하고 컴포넌트 제거 시 타이머와 갱신을 중단한다. 검색 실패나 결과 없음은 문의 입력·저장을 차단하지 않는다.
- 추천 상세는 읽기 전용 공개 FAQ 폼을 모달로 열어 작성 중인 문의 입력값을 유지한다.

## 4. 입력 항목과 검증

| 항목 | 필수 | 검증 |
|---|---|---|
| 문의 제목 `name` | 필수 | 공백 제외 5~100자 |
| 내용 `description` | 필수 | 공백 제외 10~5,000자 |
| 유형 `category_id` | 필수 | 등록된 활성 유형만 선택; 문의 상세에서 유형 자체의 생성·편집 제한 |
| 긴급도 `priority` | 필수 | 낮음·보통·높음·긴급 |
| 발생 위치/부서 `location` | 필수 | 공백 제외 2~100자 |
| 연락처 `contact` | 선택 | 입력 시 전화번호 형식 검사 |
| 첨부파일 | 선택 | JPG/JPEG/PNG/PDF/DOCX/XLSX/TXT, 문의당 최대 5개·파일당 최대 10MiB(10×1024×1024바이트) |

- 제목과 내용에는 공백만 입력할 수 없다.
- 요청자 `requester_id`는 로그인한 계정으로 자동 지정한다. **1차 정책상 직원·담당자 모두 다른 사람 명의로 문의 등록 불가**. 직원과 담당자 모두 서버 `create()`에서 타인 명의 등록을 차단한다.
- 신규 문의는 유형의 유효한 기본 담당자가 있으면 `assigned_user_id`를 자동 지정하고 초기 상태를 `assigned`로 저장한다. 기본 담당자가 없거나 비활성·외부 사용자·IT 담당자 권한 없음으로 유효하지 않으면 `received`·미배정으로 정상 접수한다.
- 발급 번호는 `ir.sequence`의 `HD-00001` 형식을 사용하며 Python 중복 검사를 통해 충돌을 막는다. 코드 기준 DB UNIQUE 제약은 아직 확인되지 않아 동시성 보장을 위한 후속 점검이 필요하다.
- 연락처는 선택 항목이다. 입력 시 숫자 9~11자리(공백·하이픈 허용)를 검증하고, 저장 시 하이픈 형태로 정규화한다.
- `create_date`, `write_date` 등 기본 생성·수정 기록은 Odoo에서 관리한다.
- 필수값, 길이, 권한, 상태 전이는 서버 측에서 검증하고 오류 메시지를 표시한다.

### 4.1 문의 유형 초기 데이터

| 코드 | 명칭 | 예시 |
|---|---|---|
| `NETWORK` | 네트워크 / 인터넷 | Wi-Fi 연결 실패, 인터넷 불가 |
| `HARDWARE` | PC / 노트북 | 부팅 오류, 블루스크린 |
| `SOFTWARE` | 소프트웨어 | 앱 실행 오류 |
| `PERIPHERAL` | 프린터 / 주변기기 | 인쇄 오류, 장치 인식 실패 |
| `ACCOUNT` | 계정 / 접근 | 로그인 실패, 계정 잠금 |
| `ETC` | 기타 | 위 유형 외 장애 |

유형의 코드 `code`는 DB UNIQUE 제약으로 유일하게 관리하며, 사용 여부는 `active`로 관리한다. 초기 유형 데이터에는 `noupdate="1"`이 설정되어 있어 이후 관리자가 수정한 이름을 모듈 업그레이드에서 덮어쓰지 않도록 한다. 유형 자체의 생성·수정·비활성화는 IT 담당자 전용 설정 화면에서만 수행하며, Ticket Form에서는 등록된 활성 유형만 선택할 수 있다. 목록과 상세 폼에서 선택 항목인 기본 담당자를 설정할 수 있으며, 빠른 생성과 사용자 생성·편집은 차단한다. 서버는 활성 내부 사용자(`active=True`, `share=False`)이면서 IT 담당자 그룹에 속한 사용자만 새 기본 담당자로 허용한다.

## 5. 상태와 업무 흐름

| 내부 값 | 표시명 | 의미 |
|---|---|---|
| `received` | 접수 | 문의 등록, 담당자 미배정 |
| `assigned` | 배정 | 처리 담당자 지정 |
| `in_progress` | 처리 중 | 담당자가 해결 작업 수행 |
| `reopen_requested` | 재처리 요청 | 요청자가 해결 결과에 이의를 제기하고 담당자의 재처리 시작을 기다리는 상태 |
| `reopened_in_progress` | 재처리 중 | 담당자가 재처리 작업을 수행하는 상태 |
| `resolved` | 해결 | 담당자가 조치 결과 작성 |
| `closed` | 종료 | 요청자가 해결 확인 완료 |

| 이전 상태 | 다음 상태 | 주체 | 조건 |
|---|---|---|---|
| 접수 | 배정 | 담당자 | 처리 담당자 지정 |
| 배정 | 처리 중 | 담당자 | 처리 시작 |
| 처리 중 | 해결 | 담당자 | **해결 내용 `resolution` 및 방식 `resolution_method` 필수** |
| 해결 | 종료 | 해당 요청자 | 해결 확인 |
| 해결 | 재처리 요청 | 해당 요청자 | **재처리 사유 필수**, 재처리 횟수 증가, 기존 해결 결과 History 보존 |
| 재처리 요청 | 재처리 중 | 담당자 | 담당자 배정 상태 확인 후 재처리 시작 |
| 재처리 중 | 해결 | 담당자 | **새 해결 내용 `resolution` 및 방식 `resolution_method` 필수** |

- 별도의 `reopen_requested`/`reopened_in_progress` 상태를 두어 요청자 재처리 접수와 담당자의 재처리 착수를 구분한다.
- **상태 전환은 화면 필드 직접 수정이나 일반 `write()`가 아닌 전용 업무 메서드/Wizard로만 수행**한다. 허용하지 않은 전이는 서버에서 거부한다.
- 상태 변경 시 이전·새 상태·변경자·시간을 History에 남긴다.
- `resolved_date`는 마지막 해결 전환 시각, `closed_date`는 종료 전환 시각을 저장한다.
- 해결 처리 시 `resolution_method`(`onsite`/`remote`)를 선택하며, 처리 방식은 상태(`resolved`)와 별개이다.
- 해결 후 재처리되면 **기존 `resolution`, `resolution_method`와 해결 시각을 History에 보존**한 후 Ticket의 현재 `resolution`, `resolution_method`, `resolved_date`를 초기화한다. 과거 해결 정보는 삭제하지 않는다.
- 재처리 시 기존 담당자는 유지하고 `reopen_count`를 1 증가시키며, 재처리 사유와 변경 주체·시각을 History에 기록한다. 재해결 시 새 해결 방식·결과·시각을 다시 저장한다.
- 종료(`closed`) 후에는 일반 직원과 담당자 모두 본문·상태·긴급도·담당자·댓글·첨부파일의 일반 수정이 불가능하다. **담당자(관리자)의 별도 아카이브·복원 관리 작업만 허용**한다.

## 6. 긴급도 관리

| 내부 값 | 표시명 | 시각적 강조 |
|---|---|---|
| `low` | 낮음 | 회색 |
| `normal` | 보통 | 파란색 |
| `high` | 높음 | 주황색 |
| `urgent` | 긴급 | 빨간색 |

- 요청자가 최초 등록할 때 지정한다. **일반 직원은 등록 후 변경 불가**이며, 담당자는 **종료 이전 문의**에 대해서만 변경할 수 있다.
- 담당자의 실제 긴급도 변경에 한해 변경 전후 값·변경자·변경 시각을 History에 남긴다. 값이 동일하면 중복 이력은 만들지 않는다.
- 저장형 계산 필드 `priority_order`를 `priority` 값에 따라 자동 산출·저장한다: `urgent=4`, `high=3`, `normal=2`, `low=1`. 사용자는 이 내부 값을 직접 수정할 수 없다.
- 담당자 전체 문의 목록 기본 정렬은 **`priority_order DESC, create_date ASC`**로 설정한다. 긴급도가 같으면 더 먼저 등록된 문의를 우선 표시하며, 긴급도 변경 시 계산 필드를 자동 갱신한다.
- 직원 내 문의 목록 기본 정렬은 `create_date DESC`(최신 등록순)이다. 별도 긴급도순 선택 정렬 UI는 확인된 구현에 없으므로 후속 사용성 검토 대상으로 둔다.

## 7. 담당자 배정

### 7.1 1차: 수동 배정
- 담당자 권한이 있는 사용자가 `assigned_user_id`를 지정·변경한다.
- 최초 배정 시 접수→배정 상태 전이와 배정 이력을 함께 기록한다.
- 재배정 시 이전/새 담당자, 변경자, 시각을 History에 남기고 **현재 처리 상태는 유지**한다.
- 미배정 문의 목록/필터를 제공한다.

### 7.2 2차: 자동 배정
- 자동 배정은 신규 문의의 `create()` 시점에만 실행하며 기존 문의나 유형 변경에는 소급 적용하지 않는다.
- 유형(`category_id`)의 기본 담당자(`default_user_id`)가 활성 내부 사용자이며 IT 담당자 권한을 보유한 경우 담당자를 자동 지정하고 초기 상태를 `assigned`로 저장한다.
- 기본 담당자가 없거나 이후 비활성화·외부 사용자 전환·IT 담당자 권한 제거로 무효화된 경우 문의 생성은 실패시키지 않고 `received`·미배정으로 유지한다.
- 자동 배정 성공 시 기존 History 모델의 `assignment` 유형으로 이전 값 `미배정`, 새 담당자, 등록자와 설명 `문의 유형에 따른 담당자 자동 배정`을 같은 트랜잭션에서 기록한다. 실패·생략 시 성공 History를 만들지 않는다.
- 클라이언트가 신규 문의에 `state` 또는 `assigned_user_id`를 임의 지정하는 기존 차단 정책은 유지하며, 입력 검증 후 서버가 결정한 자동 배정 값만 허용한다.
- 자동 배정 이후에도 담당자가 수동 재배정할 수 있으며 기존 수동 배정 History와 현재 상태 유지 규칙을 적용한다.
- 기본 담당자 설정의 유효성은 해당 필드를 새로 지정하거나 변경할 때 검사한다. 기존 설정이 나중에 무효화되었다는 이유만으로 카테고리 조회나 다른 필드 수정을 차단하지 않는다.

## 8. 댓글·첨부파일·변경 이력

### 8.1 댓글 및 첨부파일
- Odoo `mail.thread`/Chatter의 댓글(`mail.message`)과 첨부(`ir.attachment`)를 활용한다.
- 직원은 본인 문의, 담당자는 관리 가능한 문의에만 접근한다.
- 댓글의 작성자·작성 시각을 확인할 수 있게 한다.
- 첨부 조회/다운로드 역시 서버 측 권한을 확인한다.
- 첨부 형식은 JPG/JPEG, PNG, PDF, DOCX, XLSX, TXT로 제한하고, **문의당 최대 5개·파일당 최대 10MiB**를 서버에서 검사한다. 파일 형식은 확장자뿐 아니라 내용까지 검증하며 TXT는 UTF-8(선택적 BOM), CRLF를 허용한다. 임시 파일의 문의 연결, 종료 문의 업로드 및 직접 ORM 경로를 검사한다. 댓글 수정/삭제 범위와 기존 첨부 삭제·편집의 세부 정책은 미확정이며 후속 검토가 필요하다.
- 종료 상태의 문의는 직원·담당자 모두 새 댓글과 첨부 추가가 금지되며 서버에서도 차단한다. 기존 댓글·첨부의 수정·삭제까지 동일한 정책이 완전히 검증되었다고 단정하지 않는다.

### 8.2 변경 이력
- `it.helpdesk.history`에 상태 변경, 담당자 변경, 긴급도 변경, 재처리 사유, 해결 조치 변경을 기록한다.
- 항목: 대상 문의, 변경 유형, 이전 값, 새 값, 변경자, 변경 시각, 설명/사유.
- 이력은 **추가 전용(append-only)**으로 취급한다. 일반 사용자의 기존 이력 수정·삭제는 허용하지 않는다. 직원은 **본인 문의의 이력만** 읽을 수 있어야 하며, 직접 `it.helpdesk.history` 모델을 조회하는 경우에도 동일한 레코드 규칙을 적용해야 한다(**별도 History Record Rule 구현 및 직접 접근 경로 점검**).
- 현재 해결 내용은 Ticket `resolution`, 과거 해결 내용/재처리 사유는 History `description` 등으로 보존한다.

## 9. 데이터 모델 및 ERD 기준

**기준 파일: `docs/erd.drawio`**. 테이블은 Odoo 기본 사용자 1개와 프로젝트 전용 모델 4개로 구성한다. 실제 DB 테이블은 Odoo 모델 정의·설치 후 생성된다. 아래는 **논리 설계 기준**이고, Odoo 자체 시스템 필드 및 Chatter 테이블의 모든 컬럼을 나열한 물리 스키마가 아니다.

### 9.1 사용자 — `res.users` / ERD `res_users`
- 참조 필드: `id`(PK), `name`, `login`
- Odoo 기존 모델 재사용; 사용자 테이블을 별도로 생성하지 않는다.

### 9.2 문의 — `it.helpdesk.ticket` / ERD `it_helpdesk_ticket`

| 필드 | 타입/역할 | 비고 |
|---|---|---|
| `id` | ID (PK) | Odoo 기본 식별자 |
| `reference` | Char (중복 검사) | `HD-00001` 형식; 시퀀스·Python 중복 검사, DB UNIQUE 추가 검토 |
| `name` | Char | 제목 |
| `description` | Text | 장애 내용 |
| `requester_id` | Many2one → res.users | 요청자, 필수 |
| `assigned_user_id` | Many2one → res.users | 담당자, 선택 |
| `category_id` | Many2one → category | 유형, 필수 |
| `priority` | Selection | 4단계 |
| `priority_order` | Integer (저장형 계산 필드) | `urgent=4`, `high=3`, `normal=2`, `low=1`; 목록 정렬용·사용자 직접 입력 불가 |
| `state` | Selection | **7단계** (`received`, `assigned`, `in_progress`, `reopen_requested`, `reopened_in_progress`, `resolved`, `closed`) |
| `contact` | Char | 선택 연락처 |
| `location` | Char | 위치/부서, 필수 |
| `resolution` | Text | 최신 해결 내용 |
| `resolution_method` | Selection | `onsite`(현장 방문), `remote`(원격·안내); 해결 시 필수 |
| `resolved_date` | Datetime | 마지막 해결 시각 |
| `closed_date` | Datetime | 종료 시각 |
| `reopen_count` | Integer | 재처리 누적 횟수 |
| `active` | Boolean | 아카이브 여부 |

### 9.3 유형 — `it.helpdesk.category` / ERD `it_helpdesk_category`
`id`(PK), `name`, `code`(고유), `description`, `default_user_id`(선택; 2차 자동 배정), `active`.

### 9.4 이력 — `it.helpdesk.history` / ERD `it_helpdesk_history`
`id`(PK), `ticket_id`(필수 FK), `change_type`(상태/배정/긴급도/재처리/해결), `old_value`, `new_value`, `changed_by`(사용자 FK), `change_date`, `description`.

### 9.5 FAQ — `it.helpdesk.faq` / ERD `it_helpdesk_faq` (2차)
`id`(PK), `name`(필수), `answer`(필수 일반 텍스트), `category_id`(선택 FK), `keywords`, `source_ticket_id`(선택 FK·담당자 전용), `author_id`(사용자 FK·담당자 전용), `is_published`(기본 `False`), `active`(기본 `True`).

- 담당자가 직접 작성하거나 기존 해결 문의를 기반으로 **FAQ 초안**을 만든다.
- 검토 후 담당자가 수동 공개한다. 직원은 `is_published=True`인 FAQ만 조회한다.
- FAQ 화면에서 참조 원본 문의의 비공개 내용에 접근할 수 없도록 한다.

### 9.6 ERD 관계 (9개)
1. `res_users.id` → `ticket.requester_id`
2. `res_users.id` → `ticket.assigned_user_id` (선택)
3. `category.id` → `ticket.category_id`
4. `res_users.id` → `category.default_user_id` (선택)
5. `ticket.id` → `history.ticket_id`
6. `res_users.id` → `history.changed_by`
7. `category.id` → `faq.category_id`
8. `ticket.id` → `faq.source_ticket_id` (선택)
9. `res_users.id` → `faq.author_id`

댓글과 첨부는 Odoo 기본 모델의 `model`/`res_id` 연결을 재사용하므로 커스텀 테이블을 추가하지 않는다. 사용자 그룹은 Odoo 기본 권한 모델에서 관리한다.

## 10. 화면 구성

| 화면 | 사용자 | 핵심 기능 |
|---|---|---|
| F-01 공통 로그인 | 전체 | Odoo 기본 인증·그룹별 접근 제어 |
| F-02 내 문의 목록 | 일반 직원 | 본인 문의만, 7개 컬럼, 새 문의 등록·검색·필터 |
| F-03 전체 문의 목록 | 담당자 | 전체 문의, 요청자 포함 8개 컬럼, 미배정·내 담당 필터 |
| F-04 문의 등록 | 전체 | 공통 입력폼 및 서버 검증, 요청자 자동 설정 |
| F-05 문의 상세 | 전체 | 공통 정보·Chatter·변경 이력, 상태/권한별 작업 |
| F-05-W01 해결 처리 | 담당자 | 해결 방식·결과 필수 입력 후 상태 전이 |
| F-05-W02 재처리 요청 | 요청자 | 재처리 사유 필수 입력 후 **재처리 요청** 상태 전이 |
| F-05-W03 종료 승인 | 요청자 | 본인 해결 문의 종료 승인 및 종료 일시 기록 |
| F-05-W04 담당자 배정/변경 | 담당자 | 담당자 선택 후 배정·재배정 및 이력 기록 |

- **F-02 컬럼:** 번호·제목·유형·긴급도·상태·담당자·등록일. 전체 목록과 공통 검색 뷰를 사용하며 번호·제목·유형·상태·긴급도·요청자·담당자 검색, 상태/긴급도 필터와 유형·상태·긴급도·담당자 그룹화를 제공한다. 직원 화면에는 사용성이 낮은 미배정·내 담당 필터도 공통으로 나타나지만, 결과는 본인 문의로만 제한된다. 기본 최신순·Odoo 기본 페이징을 사용한다.
- **F-03 컬럼:** F-02의 7개 + 요청자. 공통 검색 뷰의 7개 상태·4개 긴급도·미배정·내 담당 필터와 유형·상태·긴급도·담당자 그룹화를 제공한다. 기본 `priority_order DESC, create_date ASC` 정렬이며 미배정 문의·보관된 문의 전용 메뉴가 있다. 유형 생성·수정·비활성화는 담당자 전용 `설정 → 문의 유형` 메뉴에서 수행한다.
- **F-04:** 양 역할 모두 등록 가능. 새 문의 요청자는 로그인 사용자로 자동 설정(담당자 대리 등록도 불가), 담당자는 미배정, 상태는 접수로 생성. 유형·제목·내용·긴급도·위치·연락처·첨부 순서. 저장·취소는 Odoo 표준 동작을 우선 사용한다.
- **F-05:** 일반 직원의 원본 정보 수정·아카이브는 접수이면서 미배정인 본인 문의로 제한하고, 등록 이후 긴급도는 변경할 수 없다. **담당자는 저장된 문의의 제목·내용·유형·발생 위치/부서·연락처를 수정할 수 없으며**, 종료 전 긴급도 조정과 별도 업무 버튼을 통한 배정·처리 시작·해결·재배정을 수행한다. 재배정 시 상태는 유지한다. 해결 상태의 요청자는 종료를 승인하거나 사유를 입력하여 **재처리 요청** 상태로 전환한다. 담당자가 **재처리 시작** 시 **재처리 중**으로 변경한다. 재처리 시 이전 해결 정보는 History에 보존하고 현재 해결 필드는 초기화한다. 종료 상태는 일반 수정·댓글·첨부가 불가능하며 담당자의 별도 보관·복원 관리 작업만 허용한다.
- **해결 후 미응답:** 1차에서는 해결 상태 유지, 자동 종료 미구현. 향후 정책 검토 시에도 요청자 승인과 시스템 자동 종료를 구분해 기록한다.
- **보안·예외:** 접근 권한, 상태 전이, 필수 해결/재처리 값, 종료 후 변경 금지 등을 UI와 서버 양쪽에서 검증한다.

## 13. 구현 현황 및 후속 결정이 필요한 항목

Day 4 코드에 구현된 정책과 아직 미확정이거나 2차로 예정된 사항을 구분한다. 일부 경로에 대한 테스트 통과는 전체 동작 보증을 의미하지 않는다.

| 항목 | 결정할 내용 |
|---|---|
| 첨부파일 | **구현:** JPG/JPEG/PNG/PDF/DOCX/XLSX/TXT, 최대 5개·파일당 10MiB, 서버 검사·TXT 인코딩 회귀 테스트. 실제 UI는 TXT 업로드와 종료 문의 차단 확인; 다른 형식·용량 한계의 브라우저 점검은 후속 |
| 댓글 | 수정·삭제 가능 주체 및 내부 메모 사용 범위 |
| 재배정 | **구현:** 재배정 시 현재 상태 유지, 담당자 변경 이력 및 접근 제어 |
| 재처리 | **구현:** `resolved → reopen_requested → reopened_in_progress → resolved`; 과거 해결 정보 History 보존, Ticket의 현행 해결 정보 초기화. 자동 회귀 테스트 포함 |
| 아카이브 복원 | **구현:** 담당자 보관·복원(종료 포함), 직원의 접수·미배정 본인 문의 보관만 허용 |
| 자동 배정(2차) | **구현:** 신규 생성 시 유형별 유효한 기본 IT 담당자를 자동 배정하고 `assigned`로 시작. 미설정·무효 담당자는 `received`·미배정 유지, 성공한 배정만 History 기록, 기존 문의 소급 변경 없음 |

| 담당자 대리 등록 | **구현:** 1차 정책상 불가. 직원·담당자의 임의 `requester_id` 지정 서버 차단 및 테스트 |
| 데이터 고유성 | **부분 확인:** 유형 `code`는 DB UNIQUE 제약 및 테스트 완료. 문의 `reference`는 시퀀스 발급·Python 중복 검사 및 자동 테스트가 있으나, DB UNIQUE 제약은 코드상 확인되지 않음. 강한 동시성 보장을 위해 DB 제약 추가 검토 |
| History 접근 | **구현:** 직원의 타인 문의 History 직접 조회 제한을 위한 Record Rule 적용 |
